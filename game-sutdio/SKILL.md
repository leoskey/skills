# 游戏全流程交付

以用户确认的游戏体验和本轮范围组织工作。制作主线是“概念与需求确认 → 设计确认 → 可玩原型 → 完整体验样段 → 内容扩充与打磨 → 发布候选”。测试、试玩和反馈迭代贯穿每个阶段，不等开发结束才开始。创建本技能、拥有项目文档或得到一句“继续”，都不能替代尚未获得的需求确认与开发授权。

## 先确定正在做什么

- 用户要求创建、调整或讨论流程/skill：只交付流程及相关使用说明；不能借机修复游戏、安装引擎或推进游戏制作。
- 用户开始制作游戏：先进入概念与需求访谈。只读现有项目和历史决定，用于提出有针对性的问题；现有代码不自动定义用户想做的游戏。
- 用户继续已有制作：核对最近明确授权的任务、已确认需求/设计和当前阶段。已有有效确认不用重复索取；“继续”只延续该任务，不能把讨论/需求阶段切换成未授权的实现。
- 用户指定单项修复：在需求与授权明确的情况下执行受影响流程，不强制重做整套访谈。若用户要求先确认需求，则先完成确认。

识别实际项目根目录，读取适用AGENTS、现有说明、需求、设计和测试入口。沿用已有结构；没有引擎或项目时不先创建工程。

## 概念与需求访谈

先说明当前理解，再针对未知且影响方向的事项，每轮询问1～3个问题。以下是访谈主题，不是一次全部发出的问卷：

1. **体验与玩家**：希望玩家获得什么体验，核心吸引点是什么，面向谁，有哪些参考游戏及喜欢/不喜欢的部分？
2. **玩法与场景**：玩家反复做什么，挑战/目标是什么，如何推进或结束，单人还是多人，在哪些设备和环境游玩？
3. **表现与规模**：2D/3D或其他表现方式、美术/音频方向、内容规模、预期游玩时长，本轮做到概念、原型还是完整版本？
4. **现实约束**：已有资源和必须保留的内容、引擎偏好、时间/成本限制、必须包含与明确不做的功能、怎样判断这轮成功？

用户没有想法时给少量候选及取舍，帮用户作决定；不能把建议写成已确认需求。只问已有上下文无法回答的关键问题，不要求用户先掌握技术术语。可使用明确标注的临时假设准备方案；不得依靠假设进入实现。

整理一份可审阅的概念/需求摘要：目标体验、核心循环、平台/输入、模式、范围内外、内容与表现目标、约束、验收条件和待定项。给需求稳定ID，记录每项是“用户已确认”“候选”还是“待定”。用户的明确授权可以委托合理细节决策，记录委托范围。

**需求门槛**：向用户展示具体摘要并请求确认。没有确认时可继续访谈、调研和文档方案，不写游戏代码、不创建场景或配置依赖。只有与当前范围相关的关键问题需要在进入下一阶段前解决，无关的后续项可保持待定。

## 设计到实现的门槛

需求确认后，提出覆盖核心循环、交互反馈、内容/关卡、美术音频、技术结构和验证办法的设计，按任务规模取舍。先让用户能审阅具体玩法和本轮计划，再询问是否按此实施。小项目可合并需求与设计的确认，前提是两者都已具体呈现。

**开发门槛**：用户已确认当前需求与设计，并明确授权本轮实现，或此前授权已经清楚覆盖这些决定。设计文件由代理写出不等于用户确认；不能自行把“草稿”改为“已批准”。“先做原型验证”只授权该原型的范围和成本，不意味着正式游戏实现获准。

确认后在已授权范围内连续开发、测试、修复，不逐文件或逐命令重复请求确认。跨越玩法方向、功能规模、平台、重要体验取舍或费用范围时，先回到相应决策阶段。发布、付费服务及外部通信按实际授权处理。

## 每批工作的约定

开发授权后，把本轮计划拆成可单独验证的小批次，每批围绕一个系统或一条完整玩家路径。开始前在现有计划中写清：

- **目标与完成条件**：关联需求ID，玩家怎样操作、看到什么结果才算完成。
- **可修改与需保护的范围**：涉及哪些文件/资产/配置，哪些已验收的行为和表现必须保持。
- **恢复与验证**：可恢复基线、所需检查、试玩步骤、运行证据及实际改动清单。
- **实验边界**：对不确定探索规定时间或尝试次数；付费生成沿用明确费用上限。达到边界就评估结果，不无限重试。

使用项目现有版本控制或可验证快照，在重要修改前和通过验收后留下恢复点。不覆盖用户未提交的工作，不自动做破坏性回滚。工具失败时说明缺失环节；不能靠静默删功能、换技术方案或削弱验证来宣布完成。

任务切换时留下短交接：有效需求/设计、授权范围、当前批次、已改文件、证据和阻塞；新会话据此续作，不靠重新猜测需求。只有获得并行工作授权时才分派代理，并按文件/场景/资产划分独立写入范围，合并后统一验证。

## 阶段产物与迭代

执行相应阶段前，读取 [阶段交付、验收与反馈循环](references/lifecycle.md)。

可玩原型用最少内容验证核心玩法是否成立；完整体验样段把代表性玩法、界面、美术、音频及目标环境串成一段接近交付品质的体验；样段通过后再扩充内容。每阶段内部都执行“定义小批目标 → 实现 → 技术检查 → 实际运行与试玩 → 评估反馈 → 修复/调整 → 留下恢复点”。需要改变已确认体验或范围时回到需求/设计确认。

阶段按本轮目标裁剪：只做概念或原型就交付到该阶段；已有项目用现有证据定位缺口，不从头重做。小型游戏可合并原型与样段，但分别说明玩法验证和品质验证的证据。阶段验收不自动扩大开发授权；已获明确授权的后续范围无需再次申请。

优先复用项目文档。没有约定时，采用以下最小组织；仅在阶段实际执行时创建，不预置空文档：

| 产物 | 默认位置 | 内容边界 |
| --- | --- | --- |
| 概念与需求 | `docs/requirements.md` | 当前目标体验、核心循环、需求ID、范围、验收条件和确认状态 |
| 设计 | `docs/design.md` | 当前玩法/交互/内容/美术与技术方案、本轮实现计划和确认状态 |
| 实现 | 项目既有源码、场景和资产目录 | 已授权的运行内容及必要配置，不硬编码技能中的工程路径 |
| 测试与反馈 | `docs/validation.md` | 需求到测试/试玩证据的对应、缺陷、玩家反馈、指标、阶段状态 |
| 迭代计划 | 复用设计或验证文档中的本轮章节 | 反馈依据、优先级、具体修改、预期改善、回归范围和授权范围 |
| 使用与交付 | 项目说明及构建产物 | 实际运行方式、支持范围、限制与对应版本 |

确认记录包含用户确认的具体范围、依据和版本/日期。需求变更后重写受影响的实现、调用方、配置、命名、注释、界面、测试和文档；旧结论保留版本归属，失效内容不混入有效规格。

## 工具按需求选择

先识别已有引擎、资产、测试方式和设备，验证工具实际可用，再选择对应技能；不为了遵循流程强制引入插件或依赖。

- Unity、Unreal、Godot、网页或其他引擎使用各自可用的编辑、构建和测试工具；项目没有选引擎时把选择及取舍放入设计，不默认Unity。
- 概念图、界面稿、建模和音频按已确认表现目标制作；Blender、图像生成及3D生成工具均为按需选择。生成资产仍需质量、来源和许可证检查。
- Game Development Studio可按需承担资产生产/准入、渲染诊断和性能对比；先读取对应技能并检查本地CLI，不把它当作完整流程的必需依赖。
- 自动测试、构建、性能采样和人工试玩各自提供不同证据。工具缺失时记录受阻项，并继续已授权且不依赖该工具的工作；不能跳过用户确认门槛。
- 多人、在线服务、VR/AR、实体共享空间、存档、支付等验证只在项目确有这些功能时启用；保留相应安全、数据和权限边界。

## 状态与完成声明

分别记录**决策状态**（草稿/待确认/已确认）和**执行状态**（未开始/进行中/通过/失败/阻塞/不适用）。测试通过不表示设计获批；批准设计不表示实现通过。不适用写明范围依据。

每次汇报说明当前阶段、产物、证据、未决事项及下一步。明确区分逻辑检查、引擎运行、构建、目标环境验证和玩家体验评价。当前承诺范围的必需项全部通过才称该轮完成；完整游戏完成还需达到用户确认的整体范围。

已经发现的问题进入反馈循环；按用户本轮授权推进，不能自行无限扩充功能或启动下一轮。用户要求暂停、返回需求或改变方向时，停止依赖旧决定的实现。
