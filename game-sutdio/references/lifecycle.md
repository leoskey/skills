# 阶段交付、验收与反馈循环

制作阶段按游戏成熟程度划分；开发、测试和反馈是阶段内反复执行的工作，不是一次性顺序工序。每轮开始明确目标和范围，结束以证据评估。阶段不适用或合并时写明依据，不能借此绕过需求或设计确认。以下主线适用于完整制作；局部修复、已有项目和仅交付原型的任务按实际范围进入或结束。

## 1. 概念探索与需求确认

**输入**：用户想法、参考作品、已有项目和访谈回答。没有确定方向时先比较少量候选，讨论玩家体验与核心循环，不先定技术实现。

**交付物**：概念摘要和需求规格，包括目标玩家、体验目标、核心玩法循环、目标/挑战/进展或结束方式、平台/输入、模式、内容与表现方向、当前范围及范围外事项、约束和可判定验收条件。

**验收标准**：

- 用户能用摘要辨认自己想做的游戏，并明确确认选定方向和本轮范围。
- 各必需需求有稳定ID、可观察结果与验证方法；代理建议、用户确认和待定项分开记录。
- 关键分歧已解决；未知技术问题可以作为用户授权的原型问题进入下一阶段，不伪装为已确定方案。
- 不强制游戏具有战斗、关卡、胜负、多人、VR或特定题材；开放玩法以自己的体验目标验收。

**未通过时**：继续访谈、整理替代方案或缩小范围，停留在概念/需求阶段。

## 2. 游戏与技术设计

**输入**：已确认需求，以及用户要求验证的未知项。

**交付物**：当前设计方案和本轮实现计划。按项目需要覆盖玩法规则及状态转移、操作与反馈、UI与无障碍、关卡/内容/进展、数值、美术/音频方向与资产清单、技术结构与数据归属、构建/运行方式及测试策略。必要时提供流程图、线框或视觉参考。

**验收标准**：

- 玩家主要路径和适用的失败/恢复路径完整；关键操作有输入、状态变化和可理解反馈。
- 设计能追溯到需求，资产和技术选择匹配目标平台、内容预算和授权成本。
- 需要视觉定调时，先筛选少量参考图或低成本概念预览，由用户确认取舍，再细化资产；不一次生成大量未评审素材。
- 本轮产物、结束条件、已知风险、测试方式与性能目标具体；数值阈值有依据，未知值标待定且不用于宣称通过。
- 用户已审阅并确认具体设计及实现范围。若只批准可玩原型，明确它要回答的问题、允许的占位内容及评价标准。

**未通过时**：设计问题回设计；核心体验或范围争议回需求。未经确认不开展依赖的游戏实现。

## 3. 可玩原型

**输入**：已确认的核心体验、原型设计、待验证问题及实现授权。

**交付物**：最少内容的可玩版本、操作入口、核心循环回归检查和试玩结论。可用灰盒与占位资产；先验证输入、相机或视角、空间可达性等适用基础，再串起一条完整核心循环。尽早产出目标平台构建，暴露导入、构建、输入或设备风险。

**验收标准**：

- 玩家能完成本轮约定的核心循环，理解目标、操作和反馈；适用的结束、失败与重试路径可用。
- 设计中列明的玩法假设有实际试玩证据和明确结论；技术运行通过与用户体验评价分别记录，不能仅凭测试绿灯判断玩法成立。
- 核心规则有直接针对生产实现的检查，游戏持续运行的证据成立；目标平台早期运行检查完成，缺设备或工具时如实标阻塞。
- 占位内容和暂未覆盖的品质要求清楚；结论说明继续、调整或放弃该方案的理由。

**未通过时**：实现问题在原型范围内修复；玩法不成立回设计，核心方向不符回需求。未解决的核心玩法或平台风险不能被美术投入或内容扩充掩盖。

## 4. 完整体验样段

**输入**：核心玩法与关键可行性已验证的原型、样段设计与已授权范围。

**交付物**：一小段具有代表性的完整体验，可是一局、一个任务、一段探索或其他适合该游戏的单位。集成玩法、UI、必要美术/动画/音频、引导与恢复流程，达到约定的代表性品质，并交付目标环境运行与试玩记录。只制作验证品质和生产方式所需的内容，不要求完整游戏的全部系统。

**验收标准**：

- 玩家能从进入到完成约定体验；系统间衔接完整，适用的异常与恢复路径可用。
- 代表性表现达到用户确认的视觉、声音与交互目标，剩余占位项不影响本轮品质判断。
- 资产进入引擎后的比例、动画、音频与性能符合约定；替换占位资产后操作、相机、碰撞及核心玩法无回退。
- 在目标环境验证体验和性能，取得用户对样段体验与品质的评审结论；不能只用编辑器结果代替目标验证。
- 能据样段识别制作成本、资产交接问题和内容扩充约束，后续计划在现有预算与授权内可行。

**未通过时**：修复集成或制作问题；体验和品质取舍回设计确认。样段的关键风险未关闭前，不批量制作依赖这些决定的内容。

## 5. 内容扩充与打磨

**输入**：验收通过的样段、确认的内容清单、优先级和本轮实现授权。

**交付物**：按小批次完成的正式内容与系统、更新后的构建、回归记录及试玩反馈。按游戏需求增加关卡、角色、任务或其他内容，不把敌人、Boss、随机地图等案例功能列为通用必需项。

**验收标准**：

- 已承诺内容清单逐项可运行，并达到样段确定的品质标准；数量增加没有破坏核心体验和性能目标。
- 每批都检查新增路径和受影响的既有路径，保留通过后的恢复点；不等全部内容完成再集成测试。
- 通过试玩评估节奏、难度、可读性和可理解性，区分观察事实与设计推断；明确反馈的处理结论。
- 新玩法或扩大内容规模先更新需求/设计及授权范围，不将反馈清单自动变成无限开发任务。

**未通过时**：按下文反馈规则定位并返回对应环节；优先解决影响后续制作的系统性问题，再继续扩量。

## 6. 发布候选与交付

**输入**：约定功能与内容已完成、版本可识别的候选构建及验收矩阵。

**交付物**：可运行/安装的约定产物、操作说明、支持范围、当前版本、已知限制、验收与反馈记录。只要求概念、设计或原型时，在对应阶段交付其产物，不强行进入发布候选。

**验收标准**：

- 当前承诺范围内必需项全部通过，阻断问题关闭；未参与讨论的人能按说明安装或启动并完成主要流程。
- 交付构建本身已在目标环境验证，证据对应同一版本；引擎运行、逻辑测试和目标设备验证分别说明。
- 功能完整性、内容品质和用户体验评审符合已确认目标；原型或样段完成不能宣布正式游戏完成。
- 交付说明与实际支持范围、已知限制一致。正式发布、商店上架和后续运营只有在用户要求并授权时执行。

**未通过时**：按反馈类型返回实现、设计或需求环节。发布候选修复后对同版产物重新验证受影响路径；缺少必需证据时保持失败或阻塞状态。

## 每批开发与内容制作

**输入**：已确认设计和本轮实现授权。

**交付物**：可运行增量、必要源码/场景/资产/配置、使用入口、直接验证生产实现的检查。复用已有结构，先完成约定的端到端体验，再扩充已授权内容。

通常先验证输入与灰盒可达性，再接核心规则和反馈，之后逐个扩展必要系统，最后替换正式资产。顺序随风险调整；不把示例中的敌人、Boss或随机地图变成所有游戏的必需功能。核心循环首次可用时就建立回归检查，并尽早生成和试玩目标构建，不等美术完成。

**验收标准**：

- 对应引擎或运行环境能成功导入/编译/启动，主要路径可操作，没有阻断错误或缺失资源。
- 操作编辑器前，用只读查询确认目标工程、场景和桥接状态，避免控制错误实例。编译失败先处理编译；优先使用引擎支持的编辑/API路径操作结构化场景和资产。
- 实际行为、界面文案和资产符合本轮设计；原型占位与正式内容的验收标准明确区分。
- 新非平凡逻辑有有效的行为检查；改动覆盖必要调用方、配置、命名和文档，保留数据保护和错误处理。
- 使用的外部内容具备可追溯来源、许可证和必要的格式/尺寸/预算验证。

资产交接要检查实际文件与引擎表现，而非只看生成任务成功：模型按需验证单位、朝向、枢轴、材质、碰撞及骨骼静止姿态/动画；音频检查真实容器、解码、削波与触发时机。替换外观时回归控制、相机、可达性和碰撞；灯光/后处理变更保留同条件前后画面，并验证保存后重新加载仍一致。

**未通过时**：在既定范围内修复并复测；若必须改变已确认设计或超出授权范围，先给出影响和选项，回到对应确认点。

## 贯穿各阶段的测试、目标环境验证与试玩

**输入**：可识别版本的候选构建、本轮需求及测试清单。

**交付物**：自动测试结果、功能与异常场景记录、目标环境验证结果、适用的性能采样、试玩观察/反馈，以及可复现缺陷。

**验收标准**：

- 必需需求覆盖正常流程、边界输入、失败/恢复及受影响的回归路径；失败不被忽略，缺设备或工具记阻塞。
- 使用真实实现及实际构建；记录源码/构建版本、环境、命令/步骤、预期/实际、报告位置和局限。
- 运行验证必须观察一段时间内的帧计数、模拟时间或预期状态变化，再记录画面与错误/警告。仅有“正在播放”标志或单帧截图不证明游戏持续运行；测试造成的临时设置在结束后恢复，尤其不能绕过目标设备的前台/追踪保护。
- 在已承诺的设备/浏览器/平台上验证启动和核心流程；编辑器、模拟器、截图或设备被发现不能代替目标运行证据。
- 性能用明确场景、指标、单位、统计口径、采样时长和阈值评估；不同工作负载/设备的数字不直接比较。
- 试玩验证操作理解、反馈、节奏、难度、美术可读性和目标体验。记录观察、玩家原话/反馈与代理推断的区别；自动检查通过不等于“好玩”。

有重复测试价值时，增加小型自动试玩，通过生产输入接口驱动实际玩家操作。遍历约定目标并记录不可达、卡住、耗时和运行错误；不能通过瞬移、直接改生命值或设置完成状态来宣称端到端通过。此类直接状态操作可以用于明确标注的逻辑测试。

含随机性的游戏记录种子及相关初始状态，在同一版本复现问题，并覆盖若干不同种子；没有随机机制时不为了测试加入随机玩法。网络/物理等非确定因素另记输入和环境，不能只凭同一种子保证复现。

条件性验证：

| 项目具备的功能 | 增加的验证 |
| --- | --- |
| 多人/在线 | 实际要求人数下的一致性、加入/退出/断连恢复、权威与输入验证、约定网络条件 |
| VR/AR或共享实体空间 | 目标设备追踪、输入、校准/重定位、中断恢复、舒适性和现场安全；不削弱设备保护来通过测试 |
| 存档/持久数据 | 保存/读取、重启、版本兼容及中断情况下的数据保护 |
| 支付/账号/云服务 | 权限、隐私与适用测试环境；费用、生产部署及外部操作遵守用户授权 |

**未通过时**：明确问题属于实现缺陷、设计问题还是需求变化，按下文反馈规则处理，不因测试失败自动重写游戏方向。每阶段只执行当前验收所需的检查，发布候选再覆盖承诺的完整范围。

## 贯穿各阶段的反馈评估与迭代

**输入**：测试结果、试玩反馈、指标变化和用户意见。

**交付物**：优先级明确的反馈清单和本轮迭代计划。每项记录依据、影响、关联需求、建议改动、预期改善、验证方法与所需确认。

| 反馈类型 | 返回阶段及动作 |
| --- | --- |
| 实现不符合已确认设计 | 在已有修复授权内回开发，复现→修复→针对性回归；不逐次重复问权限 |
| 行为符合设计但操作/节奏/体验不理想 | 回设计，提出可审阅调整与取舍，确认后实施 |
| 新玩法、平台、模式、内容规模或目标玩家变化 | 回需求，确认新范围及验收标准，再同步设计和实现 |
| 性能、稳定性或工具阻塞 | 定位可复现原因，在当前授权内修复；若需要降画质、改变目标或增加成本，先确认取舍 |
| 相互矛盾或无法复现的反馈 | 先澄清或安排已授权的针对性验证，不盲目改动 |

**验收标准**：

- 本轮优化目标、选择理由、改动范围和结束条件明确；用户新增决定进入有效规格。
- 先记录可复现问题和影响，再按授权修复；用户要求“先给问题清单”时只报告，不能顺手修复。已授权的明确缺陷仍可连续修复，避免把每个测试失败都变成新的审批。
- 用可比较证据检查是否改善，复测原问题与受影响路径，并检查是否引入新问题。
- 问题仅在符合原验收条件或用户明确变更该条件后关闭；不能通过降低标准或取消需求掩盖失败。
- 达到本轮目标后给出交付、继续迭代或返回概念探索的建议。下一轮必须属于现有授权或获得新的范围确认，不能无限自主迭代。

多次修复无效或实验预算耗尽时，停止同一种猜测，保存复现证据，缩小问题并提出下一项判别实验。需要回滚时只恢复已确认属于本批的改动并保留可恢复副本；不因达到固定失败次数而覆盖用户工作，也不自动扩大范围或提高费用。

## 最小记录

复用项目文档，不重复建管理系统：

- **确认记录**：需求/设计版本、确认范围、用户确认依据、未决项。
- **验收矩阵**：需求ID、通过条件、实现/测试位置、证据批次、执行状态、下一步。
- **反馈/缺陷**：来源、关联需求、版本、适用时的种子/初始状态、观察或复现、影响、预期/实际、建议、优先级、决策状态、修复与复验结果。
- **证据批次**：日期、源码/构建标识、环境、步骤/命令、结果、报告或媒体位置及限制；敏感日志脱敏。

## 经验来源与适用边界

参考 [rewind 的 Unity 游戏制作经验](https://x.com/rewind02/status/2110309991919853638)（2026-10-15读取正文）。本流程吸收了任务边界、恢复点、运行证据、输入路径试玩和早期构建的实践，并按通用引擎流程及用户确认要求调整。帖子中的大型项目成果、模型能力、价格和工具版本未经独立核验，不作为本技能的能力承诺或安装依据；具体工具操作以执行时可用的官方接口为准。
